# Learning RAG Autonomous Database Vector Capability

Jira: AUTO-93

## Decision

Use Oracle Autonomous Database as the first target for Learning RAG metadata and vector storage, subject to a runtime smoke check in the target OCI tenancy before implementation depends on vector indexes.

The first Learning RAG implementation should keep a portability boundary around vector storage:

- Store learning document metadata, ownership, processing status, chunk metadata, and generated artifact metadata in relational tables.
- Use `learning_materials`, `learning_chunks`, `learning_embeddings`, and `learning_ingestion_jobs` as the relational boundary.
- Keep chunk source offsets in `learning_chunks` so retrieval can cite source spans later.
- Store embeddings in an adapter-owned vector column/table only after the target ADB instance confirms `VECTOR` support.
- Keep a fallback path where embeddings can be stored as serialized arrays or in an alternate vector store if the current Always Free ADB instance does not expose the required vector capability.

## Evidence

Oracle public documentation confirms:

- OCI Always Free includes Autonomous Data Warehouse, Autonomous Transaction Processing, and Autonomous JSON Database services.
- Oracle AI Vector Search provides a `VECTOR` data type, similarity search, and vector indexes for semantic search workloads.
- `VECTOR` usage requires database compatibility at `23.4.0` or higher according to Oracle AI Vector Search documentation.

Repo deployment documentation already records:

- ADB wallet-based database connectivity is part of the private deployment model.
- ADB-related values are passed through non-secret env references and OCI Vault-backed secrets.
- The backend receives runtime database environment variables and does not read Vault directly.

## Always Free Fit

Autonomous Database is a suitable first target for this sprint because it can keep structured learning state and vector-adjacent data in one managed database boundary.

Constraints for the Learning RAG sprint:

- Treat the Always Free ADB storage budget as small. The existing repo note records roughly 20 GB per Always Free Autonomous Database instance.
- Start with text learning material only.
- Cap upload size, chunk count, and generated artifact retention before enabling broad usage.
- Keep embeddings compact by choosing an embedding model with a modest dimension count for the MVP.
- Avoid storing original uploaded file bodies in database rows if object/block storage is a better fit for larger files.

## Required Runtime Smoke Check

Before implementing vector-dependent code, run a non-secret SQL smoke check against the target ADB service:

```sql
select banner_full from v$version;

create table autoforge_vector_smoke (
  id number generated by default as identity primary key,
  content varchar2(4000),
  embedding vector
);

insert into autoforge_vector_smoke (content, embedding)
values ('smoke', vector('[0.1, 0.2, 0.3]'));

select id
from autoforge_vector_smoke
order by vector_distance(embedding, vector('[0.1, 0.2, 0.4]'))
fetch first 1 row only;

drop table autoforge_vector_smoke purge;
```

Acceptance for using native ADB vectors:

- The `VECTOR` type is accepted.
- `VECTOR_DISTANCE` or equivalent similarity query works.
- The smoke table can be created and dropped by the application migration user or a documented provisioning user.
- No credentials, wallet files, OCIDs, hostnames, or personal paths are recorded in logs or docs.

If this smoke check fails, the sprint should still proceed with the relational Learning data model and a vector-store adapter interface, but defer native ADB vector columns to a follow-up fix/spike.

## Learning RAG Data Boundary

The API and storage model must be user-scoped from the start:

- `learning_document.owner_subject` identifies the Keycloak subject that owns the material.
- `learning_document.source_type`, `source_name`, `mime_type`, `size_bytes`, `status`, and timestamps support upload and ingestion tracking.
- `learning_chunk.document_id`, `owner_subject`, `chunk_index`, `content`, `token_estimate`, and source offsets support retrieval and citations.
- `learning_embedding.chunk_id`, `owner_subject`, `model`, `dimensions`, and adapter-specific vector payload support semantic retrieval.
- `learner_profile.owner_subject` stores per-user learning preferences and level signals.
- Generated questions, summaries, and explanations store `owner_subject`, source document/chunk references, prompt-safe metadata, and created timestamps.

Jozsi and Bela must remain isolated by `owner_subject` at every query boundary. Shared material can be introduced later only with an explicit sharing model.

## Result

Recommendation: proceed with Autonomous Database as the preferred Learning RAG store for the sprint, but require the SQL smoke check before native vector DDL lands. This keeps the sprint aligned with OCI Always Free while avoiding a hard dependency on an unverified tenant/database compatibility setting.
